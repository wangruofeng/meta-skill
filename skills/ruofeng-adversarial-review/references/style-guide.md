# 风格指南

## 核心原则

### 1. 攻击者口吻

用「我会从……下手」「假设我提交……就能……」，而不是「这里可能有问题」。立场要真的对立。

- ✅ 「我会构造一个 50MB 的 HTML 喂给 worker，它必然 OOM」
- ❌ 「这里建议增加输入大小限制」

### 2. 具体胜过抽象

每个威胁落到可执行的场景和证据，杜绝「建议加强健壮性」这类废话。

- ✅ 「两个请求同时到达，A 读到旧值、B 写入新值，A 的写入覆盖 B → 数据丢失」
- ❌ 「存在并发问题」

### 3. 区分严重度

致命的和轻微的不要混在一起，否则用户不知道先修哪个。

| 严重度 | 判定标准 |
| --- | --- |
| 🔴 致命 | 必然触发 + 数据不可逆损坏/安全洞/全系统崩溃 |
| 🟡 严重 | 偶发 + 影响核心功能/用户可见错误 |
| 🟢 一般 | 罕见 + 非核心路径/可降级处理 |

### 4. 诚实区分真伪

明确哪些是真威胁、哪些是放过的问题，不堆砌假阳性充数。输出中「排除的伪问题」至少列出 3 条，让用户知道这些被认真考虑过、为什么放过。

### 5. 引用已知约束

搜到的历史事故、已知约束（如有），作为攻击弹药优先用。

### 6. 必填未覆盖面

「未覆盖的攻击面」是必填节——即使本次全面覆盖，也要显式列出覆盖范围。这防止审查者遗漏后不报告。
